Ce guide montre comment démarrer le serveur de langage Glyim et le câbler dans un éditeur qui parle le Language Server Protocol.

## Démarrer le serveur

Après avoir compilé l'espace de travail (voir le [tutoriel de démarrage](/tutorials/getting-started/)), le binaire du serveur est disponible à `target/release/glyim-lsp` :

<Code lang="bash" title="Terminal" code={`./target/release/glyim-lsp`} />

Le serveur communique sur stdio, le transport LSP standard, et publie les diagnostics avec `textDocument/publishDiagnostics` pendant que vous éditez.

## Configurer votre éditeur

Pointez le client LSP de votre éditeur sur le binaire `glyim-lsp`. La plupart des éditeurs exposent cela comme un réglage « commande de serveur personnalisée ». Un motif de configuration générique :

<Code lang="json" code={`{
  "languageserver": {
    "glyim": {
      "command": "/absolute/path/to/glyim/target/release/glyim-lsp",
      "args": [],
      "filetypes": ["glyim"]
    }
  }
}`} />

<Aside type="tip">
Utilisez un chemin absolu vers le binaire. Le serveur doit trouver les composants du compilateur, et un chemin relatif se résout contre le répertoire de travail de l'éditeur, pas le vôtre.
</Aside>

## Capacités disponibles

`glyim-lsp` implémente :

- **Diagnostics** — erreurs et avertissements du compilateur poussés pendant que vous tapez (`publishDiagnostics`), le même ensemble disponible à la demande par fichier (`textDocument/diagnostic`), et toute la session disponible à la demande par espace de travail (`workspace/diagnostic`), pilotés par le même pipeline que la CLI. Une demande par fichier porte des `relatedDocuments` : un rapport par dépendant transitif, les fichiers que le pilote réanalyse quand le fichier demandé change. Un fichier analysé sans problème répond avec un rapport complet vide ; un fichier jamais analysé répond null ; la demande par espace de travail est toujours satisfaite et signale chaque fichier analysé par identifiant croissant.
- **Navigation** — goto definition, goto type definition, goto declaration, goto implementation (les blocs `impl` derrière un trait ou un type, sur tous les fichiers analysés), find references, symboles d'espace de travail, symboles de document, et plages de pliage de document.
- **Liens de document** — les littéraux des macros d'inclusion deviennent des liens cliquables : l'argument chaîne de `include!`, `include_str!` et `include_bytes!` se résout par rapport au répertoire du document contenant (les littéraux absolus sont utilisés tels quels). Les macros hors fichier et les arguments composés comme `include!(concat!(…))` ne produisent aucun lien — la cible n'est pas connaissable depuis la source, rien n'est deviné.
- **Hiérarchie d'appels** — préparez la fonction sous le curseur (site de définition ou appel) et parcourez ses appelants entrants ou ses appelés sortants, servis depuis le même graphe de références que le renommage.
- **Surlignage** — document highlight du symbole sous le curseur, plages de sélection qui s'étendent du jeton à l'élément, et jetons sémantiques pour colorer déclarations et membres depuis le vrai arbre syntaxique.
- **Édition liée** — `textDocument/linkedEditingRange` regroupe les occurrences de même portée du symbole sous le curseur pour l'édition multi-curseurs : deux locaux de même nom dans des corps de fonction différents ne s'éditent jamais ensemble (le filtre de propriétaire de portée du graphe de références, que highlight et rename appliquent, s'applique ici aussi).
- **Hover et complétion** — informations de type au survol et suggestions de complétion depuis le def-map.
- **Aide à la signature** — indications de paramètres pendant la saisie d'un appel, avec le paramètre actif calculé depuis la position du curseur.
- **Indices d'inlay** — annotations de type en ligne sur les liaisons `let` non annotées, rendues depuis les types inférés par le vérificateur de types (les liaisons annotées et les types sans orthographe stable sont ignorés).
- **Formatage** — formatage de document pour une mise en page cohérente.
- **Renommage** — validation `prepareRename` puis renommage de symboles à travers l'espace de travail.
- **Actions de code** — corrections rapides, notamment :
  - ajouter les bras `match` manquants,
  - générer un bloc `impl`,
  - retirer les imports inutilisés,
  - auto-import pour les noms non résolus.

## Retomber sur les diagnostics JSON

Si vous pilotez l'outillage sans LSP, le compilateur émet un objet JSON par diagnostic :

<Code lang="bash" title="Terminal" code={`glyim input.g --error-format json`} />

C'est le même flux que le serveur de langage utilise en interne, ce qui le rend approprié pour les intégrations personnalisées, les vérifications CI et l'analyse de journaux.
